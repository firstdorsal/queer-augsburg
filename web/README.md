# Queer Augsburg Web

## Quiz Feature

Jeopardy-style quiz board for events. Code-split and only loaded when accessed.

-   `/quiz/control` - Host view for managing questions and awarding points
-   `/quiz/board` - Display view for audience (open in separate window/projector)

State syncs across tabs via localStorage. Export/import game data as JSON.

## Orte, Online- und Hybrid-Treffen

-   Places are stored in their own collection. Editors pick a place from the dropdown in the
    meeting editor or create one there ("Neuen Ort anlegen" opens the map). The server copies
    name and coordinates into the meeting (`location`). A meeting takes place in person, at a
    place or at "Ort wird noch bekanntgegeben" (`place_to_be_announced`, shown on the card,
    in the iCal feed and in the overview instead of a place; never both), online, or hybrid:
    online and in person. The editor chooses "Vor Ort", "Hybrid (vor Ort und online)" or
    "Nur online"; it keeps a chosen place while "Ort wird noch bekanntgegeben" is ticked (the
    server drops it on save) and removes it for "Nur online" (it comes back when switching
    back). Everything that shows a venue reads it the same way (`meetingVenue` in
    `src/places.ts`, `Meeting::venue` on the server); hybrid meetings show both parts.
    "Hybrid" is not stored: it is online details next to a place or "Ort wird noch
    bekanntgegeben". The editor keeps the chosen format itself (`FormatState`), because a
    hybrid meeting whose place is not chosen yet looks like an online one; the server would
    save it as online only.
-   Online and hybrid meetings have a platform and an optional link. A link is either
    public or, by default, members-only: then it is never part of the meeting list, the iCal
    feed or the local cache. Verified members (membership approved) and editors load it on
    demand from `GET /api/meeting_link/?m=<id>` ("Link anzeigen").
-   API: `GET /api/places/`, `POST /api/create_place/` (both `UpdateMeetings`),
    `GET /api/meeting_link/`, the public `GET /api/meetings_overview/` (below); see `/docs`. Types in `src/apiTypes` are generated by ts-rs
    (`cargo test` in `server/`).
-   Logic and tests: `src/places.ts`, `server/src/place_rules.rs`; place names are compared
    with the same key in both (shared cases in `server/src/place_key_cases.json`).
-   The migration of the old data is in `server/migrations/2026-10-21-places/`.

## Öffentliche Terminübersicht (für KI-Assistenten)

`GET /api/meetings_overview/?from=YYYY-MM-DD&to=YYYY-MM-DD` lists the published meetings
(never planned or deleted ones) as small JSON, for the AI models members use with the bulk
import and for other tools. No login; any origin may read it (CORS `*`); answers are cached
for 5 minutes.

-   `from`/`to`: first and last day in Berlin time, both optional (`from` defaults to today,
    `to` to no end), 2000-01-01 to 2099-12-31. Bad dates, `to` before `from` and unknown
    parameters get a 400 with an English explanation.
-   Answer: `time_zone` ("Europe/Berlin"), `meetings` sorted by start, at most 500 (the
    earliest), `truncated` if there are more. Per meeting `id`, `start` ("2026-10-27T19:00",
    Berlin), `title`, `place` (name or null), `online`, `platform`,
    `place_to_be_announced`, `cancelled`, `url` (the meeting page, from the server's
    `uiOrigin`), `hybrid` (online and in person; since 2026-10 `online` can come together
    with `place` or `place_to_be_announced`). No descriptions and no links to online
    meetings.
-   Types: `MeetingsOverview`/`MeetingSummary` (ts-rs); fields are only ever added. The
    prompt's field list (`OVERVIEW_FIELDS` in `src/bulkPrompt.ts`) is checked against them at
    compile time.
-   Code: `server/src/methods/meetings_overview.rs`, query `get_published_meetings_between`
    in `server/src/db.rs` (index on `meetings.time`).

## Mehrere Treffen anlegen (Bulk-Import)

For members with the `UpdateMeetings` capability, the meeting list shows **"Mehrere Treffen (JSON)"** next to "Neues Treffen". Instead of filling the form once per meeting, the member

1. copies a generated prompt into an AI model of their choice and describes the meetings there. The prompt contains today's date, the stored places from `GET /api/places/`, allowed tags and limits, and the stored meetings from 24 hours ago on (active and planned, at most the next 50, with start, title, place or "Ort wird noch bekanntgegeben" and/or online platform, and status, cancelled ones marked), so the model does not create them again and asks when a described meeting looks like one of them; for published meetings beyond that it explains the public overview (above), which models that can fetch web pages use themselves. It tells the model to ask back for missing date, time or place, and to ask once, together, for the optional organiser, price, age restriction, accessibility and trigger warnings. Places and meetings are loaded fresh when the dialog opens (`GET /api/get_meetings/?from=…`, never from the offline cache); if that fails, the dialog offers "Erneut versuchen" and nothing can be pasted yet,
2. pastes the model's answer (a JSON array; code fences and chat text around it are tolerated). A meeting has `"place"` (a place name) or `"place_to_be_announced": true` (not both), `"online": {"platform", "link", "link_public"}`, or for a hybrid meeting `"online"` and one of the two; links are members-only unless `link_public` is true. `"online": true` stands for an online meeting without details, `false` for none. A members-only link that also appears in the title or description gets a warning, because those are public,
3. reviews the drafts: place names are matched to the stored places (same name key as the server, accents ignored when unambiguous); for an unknown name the member picks a stored place or creates one ("Neuen Ort anlegen", map), which then applies to every meeting with that name. Each draft is compared with the stored meetings from 24 hours ago on and with the other drafts: at most an hour apart at the same place or online on the same platform (a hybrid meeting matches either way; a place to be announced is no place to compare), or on the same Berlin day with a similar title (same or mostly the same words, ignoring accents, numbers, short function words and the group's name). Errors block, hints (past dates, ignored fields, possible duplicates) do not; "Nicht anlegen" leaves a draft out, and stays set while the JSON is edited as long as that draft's title, start and venue do not change,
4. creates the remaining meetings in one request (`POST /api/create_meetings/`, at most 50, each with `place_id` or `place_to_be_announced: true`, `online`, or `online` and one of the two). Right before that, the dialog loads the stored meetings again; if a draft got a new duplicate hint in the meantime (e.g. another editor added a meeting), nothing is sent and the member checks again. The server validates every meeting first, copies name and coordinates from the stored place, and creates nothing if one is invalid. **Every meeting is created as "Geplant"** (the request has no status; the server sets it): the list switches to "Geplante Treffen", where an editor opens each meeting and sets it to "Aktiv" to publish it.

Code: `src/bulkImport.ts` (format, parsing, validation), `src/meetingDuplicates.ts` (duplicate check), `src/bulkPrompt.ts` (prompt), `src/berlinTime.ts`, `src/components/BulkImportMeetings.tsx` (UI), server side `server/src/meeting_validation.rs`, `server/src/place_rules.rs` and `server/src/methods/create_meetings.rs`. Client and server validation (including the online details) are mirrored and both tested against `server/src/meeting_validation_cases.json` (where the import words a rule differently because it talks about JSON fields, the case has a `client_error`); change rules on both sides and in that file together.

The "Prompt kopieren" button needs `clipboard-write=(self)` in the `permissions-policy` header: `server/config.yml` in the image, and `deployment/templates/config/qa-web.yml`, which production mounts over it. Without clipboard access the prompt is shown for manual copying.

## Dokumente

Internal documents at `/dokumente` (`/dashboard` forwards there). Verified members, meeting editors and holders of the capability `UpdateDocuments` read them; only holders write. Readers get rendered Markdown over HTTP: what was last saved (within 10 seconds of typing, longer while a save is failing); it updates on reload. Plain Markdown through `Md`, without images (`disallowedElements`), tables (they would need remark-gfm) or raw HTML.

-   **Text:** changes only through the live editor. `documents.state` (Yjs) is the source of truth; `content` and `title` (the first `# ` heading) are derived on every save. A document gets its state once, in `create_document`: two independent states of one text would merge into the text appearing twice.
-   **Groups:** `group_ids` on the document is the membership, so a document can be in several groups in one atomic write. The order of groups and of documents in a group are separate lists that only express a wish (`apply_order`): ids they do not know follow alphabetically, so a reorder race can never lose a document. Documents without a group are listed alphabetically under "Ohne Gruppe". The page opens the first document of the first group, so sorting decides the start page.
-   **Search:** `GET /api/search_documents/?q=`. Every term must occur in the title or text, also inside a word ("satzung" finds "Vereinssatzung"), ß finds ss. Matching runs in Rust on the original text (`document_search.rs`). MongoDB's `$text` matches whole words only, which fails for German compounds.
-   **Versions:** kept automatically: the text before the first change of a session, then at most every 10 minutes while it changes, and when a room closes; never twice the same, at most one a minute, the newest 50. Restoring replaces the text as an ordinary edit, for everyone at once.

### Live editing

`GET /api/document_sync/{document_id}`, a WebSocket speaking the y-websocket protocol (not in the OpenAPI docs). Server: `server/src/document_rooms.rs`, one actor task per open document owning the yrs `Doc`, and `server/src/methods/document_sync.rs`. Browser: `src/documentEditor/`, a lazy chunk of about 200 kB gzip that is kept out of the service worker's precache, so guests do not download it. Nothing outside that folder may import from it except the lazy import in `pages/Documents.tsx`.

-   **Before the upgrade, as HTTP status** (browsers show these only as close code 1006): 503 restarting, 403 wrong `Origin`, 401 no session. The `Origin` check is the only barrier against other websites: the session cookie is `SameSite=None` and CORS does not cover WebSockets.
-   **Close codes the editor explains:** 4401 session gone, 4403 no permission, 4404 deleted, 4413 too large, 4422 stored state damaged, 4400 broken message; 1011 server error, 1012 restart, 1013 too many rooms or connections. `src/documentEditor/connection.ts` decides what follows: 4401 and 1006 renew the session and reconnect, other 44xx stop, the rest reconnects.
-   **Name and colour** in the editor come from the server, which overwrites them in every awareness update.
-   **CSP:** `connect-src` needs `wss://` of the API, as `https://` does not cover it (`CSP_CONNECT_SRC` in the compose template). CodeMirror runs in a shadow root, because the CSP blocks its `<style>` element in `document` but not the constructable stylesheet it uses there. So global CSS does not reach the editor: its styles go through `EditorView.theme`. Remote cursors use classes (`remoteSelections.ts`), because the caret of y-codemirror.next sets a `style` attribute.
-   **Undo:** no `history()` and no `basicSetup`: their undo takes back other people's text too.
-   **Limits** are consts at the top of `document_rooms.rs`, measured with 10 million keystrokes. A document's state never shrinks, even after a reload; at 6 000 000 bytes further growth is refused with 4413, and the text moves to a new document.
-   **Allocations:** `CappedAllocator` is what stands between an 8-byte frame declaring billions of entries and the process being killed. `max_message_size` cannot stop that. It relies on the yrs decoders using `try_reserve`; `tests/document_rooms.rs` sends such frames.
-   **Links** between documents are stored in their text, so `/dokumente/<id>` has to stay valid.
-   yjs, y-websocket, y-codemirror.next and yrs are pinned exactly: both sides speak one protocol.

Rules shared with the server: `server/src/document_validation_cases.json`, run by `document_rules.rs` and `src/documents.test.ts`.

Not covered by CI, to check by hand with two browsers through traefik before a deploy that touches this: cursors and console free of CSP errors, typing across a session renewal (10 minutes), `docker stop` while typing, 30 seconds offline, restoring a version, a phone with its on-screen keyboard, Safari.

## Map and address search (OpenStreetMap)

"Neuen Ort anlegen" shows OpenStreetMap tiles and searches addresses with Nominatim, directly from the browser. Their usage policies are kept in `src/osm.ts`: the canonical tile URL `https://tile.openstreetmap.org/…` (no a/b/c subdomains), visible attribution, at most one search per second and only on explicit search (no search-as-you-type), and a Referer — the site sends `Referrer-Policy: no-referrer`, so tiles and searches override it per request and send only the origin. Without the Referer, OSM blocks the tiles (403, "does not comply with the tile usage policy").

Security headers live in two files that must be changed together: `server/config.yml` (baked into the image) and `deployment/templates/config/qa-web.yml` (production mounts its rendered copy, `deployment/results/config/qa-web.yml` on turing, over it; changes there need `docker compose -p results up -d --no-deps --force-recreate qa-web`). Their CSP must allow `https://tile.openstreetmap.org` in `img-src` and `https://nominatim.openstreetmap.org` in `connect-src`; `src/osm.test.ts` checks both files.

## Tests

```sh
pnpm test        # type-checks src incl. tests (tsconfig.test.json), then runs vitest
cd ../server && cargo test   # server tests; also regenerates src/apiTypes via ts-rs
TEST_MONGODB_URI=mongodb://localhost:<port> cargo test   # plus the tests against a real MongoDB
```

`pnpm test` and `pnpm build` both run `fix-react-markdown-types`, which deletes `react-markdown/lib/complex-types.ts`: react-markdown 8 ships that TypeScript source file, and it does not compile against the Preact JSX types. Test files are excluded from `pnpm build` because they import the shared fixture from `server/`, which is outside the web Docker build context. CI runs both test suites (`test-web`, `test-server`) before building images.
