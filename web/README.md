# Queer Augsburg Web

## Quiz Feature

Jeopardy-style quiz board for events. Code-split and only loaded when accessed.

-   `/quiz/control` - Host view for managing questions and awarding points
-   `/quiz/board` - Display view for audience (open in separate window/projector)

State syncs across tabs via localStorage. Export/import game data as JSON.

## Orte und Online-Treffen

-   Places are stored in their own collection. Editors pick a place from the dropdown in the
    meeting editor or create one there ("Neuen Ort anlegen" opens the map). The server copies
    name and coordinates into the meeting (`location`) and refuses meetings without a place,
    except online meetings.
-   Online meetings ("Online-Treffen") have a platform and an optional link. A link is either
    public or, by default, members-only: then it is never part of the meeting list, the iCal
    feed or the local cache. Verified members (membership approved) and editors load it on
    demand from `GET /api/meeting_link/?m=<id>` ("Link anzeigen").
-   API: `GET /api/places/`, `POST /api/create_place/` (both `UpdateMeetings`),
    `GET /api/meeting_link/`; see `/docs`. Types in `src/apiTypes` are generated by ts-rs
    (`cargo test` in `server/`).
-   Logic and tests: `src/places.ts`, `server/src/place_rules.rs`; place names are compared
    with the same key in both (shared cases in `server/src/place_key_cases.json`).
-   The migration of the old data is in `server/migrations/2026-10-21-places/`.

## Mehrere Treffen anlegen (Bulk-Import)

For members with the `UpdateMeetings` capability, the meeting list shows **"Mehrere Treffen (JSON)"** next to "Neues Treffen". Instead of filling the form once per meeting, the member

1. copies a generated prompt into an AI model of their choice and describes the meetings there. The prompt contains today's date, the stored places from `GET /api/places/`, allowed tags and limits, and the stored meetings from 24 hours ago on (active and planned, at most the next 50, with start, title, place or online platform, and status, cancelled ones marked), so the model does not create them again and asks when a described meeting looks like one of them; for published meetings beyond that it names the public iCal feed. It tells the model to ask back for missing date, time or place. Places and meetings are loaded fresh when the dialog opens (`GET /api/get_meetings/?from=…`, never from the offline cache); if that fails, the dialog offers "Erneut versuchen" and nothing can be pasted yet,
2. pastes the model's answer (a JSON array; code fences and chat text around it are tolerated). A meeting has either `"place"` (a place name) or `"online": {"platform", "link", "link_public"}`; links are members-only unless `link_public` is true. `"online": true` stands for an online meeting without details, `false` for none. A members-only link that also appears in the title or description gets a warning, because those are public,
3. reviews the drafts: place names are matched to the stored places (same name key as the server, accents ignored when unambiguous); for an unknown name the member picks a stored place or creates one ("Neuen Ort anlegen", map), which then applies to every meeting with that name. Each draft is compared with the stored meetings from 24 hours ago on and with the other drafts: at most an hour apart at the same place (or online on the same platform), or on the same Berlin day with a similar title (same or mostly the same words, ignoring accents, numbers, short function words and the group's name). Errors block, hints (past dates, ignored fields, possible duplicates) do not; "Nicht anlegen" leaves a draft out, and stays set while the JSON is edited as long as that draft's title, start and place do not change,
4. creates the remaining meetings in one request (`POST /api/create_meetings/`, at most 50, each with either `place_id` or `online`). Right before that, the dialog loads the stored meetings again; if a draft got a new duplicate hint in the meantime (e.g. another editor added a meeting), nothing is sent and the member checks again. The server validates every meeting first, copies name and coordinates from the stored place, and creates nothing if one is invalid. **Every meeting is created as "Geplant"** (the request has no status; the server sets it): the list switches to "Geplante Treffen", where an editor opens each meeting and sets it to "Aktiv" to publish it.

Code: `src/bulkImport.ts` (format, parsing, validation), `src/meetingDuplicates.ts` (duplicate check), `src/bulkPrompt.ts` (prompt), `src/berlinTime.ts`, `src/components/BulkImportMeetings.tsx` (UI), server side `server/src/meeting_validation.rs`, `server/src/place_rules.rs` and `server/src/methods/create_meetings.rs`. Client and server validation (including the online details) are mirrored and both tested against `server/src/meeting_validation_cases.json` (where the import words a rule differently because it talks about JSON fields, the case has a `client_error`); change rules on both sides and in that file together.

The "Prompt kopieren" button needs `clipboard-write=(self)` in the `permissions-policy` header: `server/config.yml` in the image, and `deployment/templates/config/qa-web.yml`, which production mounts over it. Without clipboard access the prompt is shown for manual copying.

## Tests

```sh
pnpm test        # type-checks src incl. tests (tsconfig.test.json), then runs vitest
cd ../server && cargo test   # server tests; also regenerates src/apiTypes via ts-rs
```

`pnpm test` and `pnpm build` both run `fix-react-markdown-types`, which deletes `react-markdown/lib/complex-types.ts`: react-markdown 8 ships that TypeScript source file, and it does not compile against the Preact JSX types. Test files are excluded from `pnpm build` because they import the shared fixture from `server/`, which is outside the web Docker build context. CI runs both test suites (`test-web`, `test-server`) before building images.
